## Source architecture and acceptance split

The original AMA M7 roadmap calls for a generic read-only synthetic reference, controlled E0 classified-read admission, a nonproduction simulated consequential effect, optional memory profiles, durable resume, outcome evaluation, evidence, and independent acceptance. One agent instance cannot necessarily exercise all optional cognitive profiles, so M7-E has six **separate reference profiles** belonging to the same generic synthetic identity, plus an independent host-runtime integration fixture.

The user-approved milestone split is:

- **M7-E:** fully specified, CI-tested synthetic engineering integration using source-derived M0–M6 contracts, the F8.1–F8.6 security adapter and disposable PostgreSQL. This state **never** grants `DEPLOYABLE` or `ACTIVE`, even if every test passes.
- **F8.7:** release-pinned real CDX policy/runtime binding, authenticated authority and independently controlled SPETL evidence. Production enforcement not yet established.
- **M7-O:** real C4/C5, operational readiness and independently authorized human acceptance on production-representative systems; no CI synthetic report can substitute.

The universal `docs/architecture/AMA.md`, historical v1 manifest and CDX constitutional core remain unchanged.

## Synthetic source-derived reference matrix

The reference suite is generated by `packages/agent-model/conformance/ama_m7_integration.py`, using the fixture-construction and validators originally tested for each milestone. The generated instances are archived under the CI job artifact—not registered in FFOS or activated.

| Reference profile | Existing source implementation exercised | Core verification |
| --- | --- | --- |
| MINIMAL_MEMORY_OFF | M1 v0.2 candidate bundle/manifest/commands/capabilities | Full graph and schema closure; memory disabled |
| E0_CLASSIFIED_READ_PRECHECK | M2 identity, mandate, recipient, purpose, scope | No blanket E0 exemption or agent-issued authority |
| MEMORY_ON_PROFILE | M3 model/instruction/planner, retrieval and memory quarantine | Optional memory ON, bounded sources, pinned modules |
| DURABLE_UNKNOWN_AND_RECONCILIATION | M4 run/step/attempt/effect/receipt/reconciliation graph | Immutable source/digest reference closure |
| EVALUATION_TEN_AXIS | M5 ten axes, holdout, repetition and oracle evidence | Synthetic test-double outcome and evidence metrics, never live independent acceptance |
| OPERATIONAL_CANARY_REVIEW | M6 version compatibility, health, incidents, canary/rollback proposal | Qualified candidate recommendation, no traffic-shift or approval |

The report requires six passing profiles **and** explicitly reports both memory OFF and memory ON; a single generic agent need not implement optional cognition. Each profile records the exact candidate contract version, agent digest and fixture-content digest for inspectability. Cross-profile identity remains `SYNTHETIC.AGENT` with pinned versions, but the agent definitions vary by optional profile. Cross-profile digest differences are therefore intentional, not a claim that one immutable registration contains contradictory memory settings.

A dedicated negative suite rejects source/agent-pin tampering, E0 recipient substitution, M5 false ALLOW, M6 revoked capability, fake F8.7 release promotion, missing preflight blockers and attempted self-acceptance.

## End-to-end host-runtime engineering fixture

`packages/agent-runtime/tests/m7e-end-to-end-pg.test.mjs` sets up an actual disposable PostgreSQL schema with the existing v1 registry and additive M4/M6 migrations. Its **host adapter** is distinct from the candidate v0.2 model. The host uses a test-only ACTIVE-looking fixture that cannot become a real registered agent or production activation.

Four test trajectories:

1. **Classified E0:** Independent test-double recipient/purpose/grant and classification checks, the actual full-surface `CDXF8VerifiedAdapter` in read-only mode, fresh policy/fact verification and append-only read evidence; no confidential real data.
2. **Bounded E2:** M4 `DurablePgCoordinator` + `M6GuardedAdmission` + actual `AgentEffectGate` and complete F8 multi-surface mandatory-controls consumer. A dummy change goes only into a disposable CI PostgreSQL table. The callback cannot self-accept the result; run becomes HOLD/UNKNOWN, forged receipt is rejected, independent-test-double reconciliation resumes the run, then completes without repeating the effect.
3. **Fail-closed F8 boundary:** Absent security policy, invalid anchor or policy outage cannot invoke a callback; evidence, replay and effect checks remain restrictive.
4. **Independent-authority emergency containment:** M6 incident action fences the M4 lease, preserves prior run events and prevents any newly admitted run for a suspended version.

The F8 policy adapter, identity, decision signatures, custody and release ports are **real implementation contracts but synthetic CI test doubles**. The upstream CDX status is `PRE_RELEASE`, not production released. A test asserting a pretend released policy **is never proof** of F8.7.

## Acceptance and proof requirements

The M7-E engineering gate requires:

- Full M0–M6 and F8 source audit CI success without removing or weakening previous tests.
- Six valid, source-pinned synthetic reference profiles, distinct memory ON/OFF and negative regression tests.
- Actual PostgreSQL cross-layer E0/E2 execution, bounded effect with no actual remote effect, explicit UNKNOWN before independent reconciliation, and verified absence of duplicate effects.
- Real F8 consumer code exercised with externally injected *test* identities, policy and custody, never a bypass around its mandatory surface selection.
- Incident suspension integrated with admission, existing-run fencing and immutable evidence.
- A generated, inspectable report that lists all genuine external gates and guarantees `deployment_authorized=false`, `registration_authorized=false`, `independent_accepted=false` and `m7_o_verified=false`.

A green engineering gate can be recorded as **M7-E ENGINEERING CANDIDATE VERIFIED** after the latest complete CI run succeeds. It does **not** authorize human acceptance, deployment, release of CDX, database migration, first-class agent registration, real-world external effects or draft PR merge.

## Residual M7-O requirements

F8.7 must establish a human-authorized CDX 1.0 release and fully authenticated runtime policy, source graph/revocation, SPETL custody and independently governed estate binding. M5 must then verify actual final states and C4/C5 against independently trusted oracles. M6 requires real telemetry, incident routing, approval/rollback controls and production data governance. Reviewers must independently sign and accept the complete evidence chain. Only then may the governing external authority consider an agent's activation.

**M7-E completion means engineering readiness for that integration—not completion of the universal agent system's operational release.**
